# 预算

预算限制一次操作投入的搜索工作、运行时间和恢复次数。每个预算都有单位、拥有者、计费范围和耗尽处理；沿着调用链理解这些信息，才能判断一次超时的实际原因。

## 单位与时钟

| 单位 | 计量内容 | 使用位置 |
| --- | --- | --- |
| 节点展开数 | A* 实际展开的搜索节点 | `PlanningSession` |
| 服务器 tick | 游戏推进的 tick 数 | 导航、旅行、取货与补给超时 |
| 活动 tick | 总 tick 差扣除明确挂起的区间 | `ExecutionScope` |
| 规划纳秒 | 单调时钟测得的规划耗时 | 配方规划和协作式搜索切片 |
| 次数 | 重规划、补给或重复尝试的数量 | 各业务拥有的计数器 |
| 实际时间 | 单调时钟测得的经过时间 | 异步库存查询、运行诊断与测试程序时限 |

服务器 tick 预算随游戏速率变化。持续达到 20 TPS 时，1200 tick 约为一分钟；80 TPS 时约为 15 秒。TPS 下降时，相同 tick 数耗费更长实际时间。配方规划的纳秒限制随实际计算耗时计量。

“活动”表示执行范围没有明确挂起。普通区块、数据库或菜单等待仍计入该范围的活动时间。资源等待通过 `TravelFuelWaitDriver` 挂起原执行，挂起区间从它和受通知子执行的超时中扣除。恢复后继续使用已花费的额度。

`ReplenishSuppliesFlow` 的库存查询与来源排序共用10秒实际时间上限，服务器提速不会缩短这个查询期限。查询在后台继续，期限从提交查询开始计算；失败时取消未完成的查询与排序。外层执行和无进展限制仍分别生效。

## 拥有者与嵌套

```text
材料获取／业务执行范围
  → 来源尝试范围
    → 旅行范围
      → 区域接近或传送范围
        → 局部导航／飞行范围
          → 路径段／Action 范围
```

各层分别记录开始 tick 和自己的限额。子操作执行期间，父操作的时间也在增长。创建新子操作会创建子范围；同一个父范围的已用时间继续保留。

`ExecutionScope.remainingActiveTicks()` 在同步嵌套调用中采用当前调用链最早的截止点。区域接近用这个值判断是否需要提前停止出发并预留返程时间。

例如子飞行还允许 5000 tick，但父来源只剩 1000 tick：这次操作仍受父范围剩余时间限制。需要同时查看超时所属层级、当时活动子操作和已用时间。

## A* 搜索预算

| 项目 | 默认值 | 范围与行为 |
| --- | --- | --- |
| `maxExpandedNodes` | 8192 | 每个 `PlanningSession` 的节点上限 |
| `expansionsPerTick` | 16 | 每次搜索切片的节点展开上限 |
| 搜索切片计时 | 约 4 ms | `PathFinder` 传入的协作式时间限制 |
| 同一路径边访问 | 最多 10 次 | 一个 `LocalNavigationFlow` 中保留计数 |

搜索切片先保留最多 4 次基础展开，再根据剩余切片时间继续，整体受调用者节点数上限约束。候选发现和过期队列清理有额外局部限额。几何检查属于不可拆分操作，因此单次调用仍可能超过协作式时间限制。

新的 A* 会话重新获得节点额度。例如完成部分路径后继续搜索，或搜索起点发生位移而重建会话。`PathFinder` 累计统计已展开节点，但当前 8192 上限按会话执行。因此一次局部导航的累计访问节点数可以超过 8192。

节点上限触发后，允许部分路径的请求可以返回可执行前缀，再从实际位置继续。整次导航的规划和移动 tick 继续累计。具体目标仍须满足自己的完成条件。

## 局部导航的累计预算

`NavigationBudget` 在 `LocalNavigationFlow` 创建时，按初始水平距离 `d` 捕获额外额度：

```text
A = ceil(min(12000, max(0, d - 128) × 16))
规划上限 = 4800 + floor(A / 4)
移动上限 = 4800 + A - floor(A / 4)
执行范围总上限 = 9600 + A
```

规划阶段每次推进占用一个规划 tick，执行路径阶段占用一个移动 tick。水中规划恢复等操作也计入其所在阶段。部分路径切换和位置偏移重规划保留这两个计数器。

| 初始水平距离 | 规划 tick | 移动 tick | 总 tick | 20 TPS 下总时限 | 80 TPS 下总时限 |
| --- | --- | --- | --- | --- | --- |
| ≤128 格 | 4800 | 4800 | 9600 | 8 分钟 | 2 分钟 |
| 500 格 | 6288 | 9264 | 15552 | 约 13 分钟 | 约 3.2 分钟 |
| ≥878 格 | 7800 | 13800 | 21600 | 18 分钟 | 4.5 分钟 |

这些时间表示外层执行范围允许的最大活动时长。规划或移动额度可以单独先耗尽；表中数值用于理解限额与速率，实际行程耗时取决于路径、障碍和等待。

规划额度耗尽报告 `PATH_TIMEOUT`；移动额度或执行范围时限耗尽报告 `TIMEOUT`。节点耗尽且没有允许的可执行前缀时，也可报告 `PATH_TIMEOUT`。搜索确认没有可执行路径时报告 `NO_PATH`。

## 旅行、飞行与来源预算

| 拥有者 | 当前基准或公式 | 额外计量 |
| --- | --- | --- |
| `TravelToFlow` | 36000 tick | 加已记录的补给准备余量；受控重规划最多 3 次 |
| `PortalJourneyFlow` | 12000 tick | 加距离及受限补给准备余量 |
| `ElytraFlightFlow` | 3600 + ceil(水平距离) tick | 在创建时捕获飞行距离 |
| `SupplySourceFlow` | 24000 tick | 加往返距离、容量恢复和补给准备余量 |
| `PrepareSupplyFlow` | 24000 tick | 加背包整理实际记录的取盒、返回与外部周转时间 |
| `AtlasSupplyLoadFlow` | 25200 tick | 规划与准备共用外层时限，并传递同一背包周转余量 |
| `AcquireProductionFlow` | 288000 tick | 覆盖收集、生产与结算的外层时限 |

`FlightTimeBudget` 按水平距离每格增加一个 tick，往返余量为两倍。它捕获出发距离，执行中保留该额度。长途区域接近使用最多 4096 格的飞行航段，并具有自己的航段数量和返程时限；飞行阶段仍受所有父范围限制。

表内基准按代码中的 tick 常量列出。36000 tick 在 20 TPS 下是 30 分钟，在持续 80 TPS 下约为 7.5 分钟；288000 tick 分别约为 4 小时和 1 小时。

`TravelToFlow` 的基准没有按总距离直接增加。它的传送和接近子流程可以有距离余量，父旅行基准仍会约束整个行程。`SupplySourceFlow` 使用水平坐标距离计算飞行式往返余量；跨维度路线本身的实际距离另由旅行规划器估价。

## 补给预算与时间余量

`ResourceMaintenance` 保存资源类型的累计活动 tick 和补给次数。同一资源类型正在维护时，禁止再次进入该类型；燃料维护也限制食物外出补给。

| 项目 | 当前限制与范围 |
| --- | --- |
| 烟花补给次数 | 一个维护上下文累计最多 16 次 |
| 食物补给次数 | 一个维护上下文累计最多 16 次 |
| `fuelTicks` / `foodTicks` | 各类型在同一上下文累计最多 24000 tick |
| `ReplenishSuppliesFlow` | 一次实例最多 24000 活动 tick，保留来源替换和部分取得进度 |
| 重新查询来源 | 一次补给实例最多 3 轮 |

`BoundedTimeAllowance` 将观察到的补给准备时间作为父操作的附加余量，并限制累计上限。完成一个补给、切换来源或重规划都应保留已经记录的余量。

附加余量是在父操作时限中补偿已发生的额外工作；资源策略还有自己的累计消耗和次数限制。两者需要分别阅读。例如已完成 2000 tick 补给，父操作可以增加记录的余量，但资源上下文的已用 2000 tick 仍继续保留。

目前补给余量由相关父流程显式汇报和累计。运输准备与实际获取持有不同维护上下文，计数范围也随之分开。调用边界见[补给与执行恢复](../supply/maintenance#容量与上下文)。

## 配方规划预算

`MaterialProductionPlanner` 使用单次限制和共享任务限制：

| 项目 | 单次规划 | 共享任务预算 |
| --- | --- | --- |
| 展开深度 | 12 | 每次遵循相同深度限制 |
| 展开次数 | 10000 | 累计 50000 |
| 规划耗时 | 100 ms | 累计 500 ms |
| 规划次数 | — | 最多 16 次 |

时间使用 `System.nanoTime()` 的单调时钟差。共享任务预算对象复用于重新规划时，继续保留已用次数、展开数和耗时。生成新的预算对象会建立新计数范围。配方循环、单次或累计预算耗尽形成具体缺口原因；后续实物合成有自己的执行范围。

## 耗尽后的责任

| 耗尽位置 | 后续 |
| --- | --- |
| 局部搜索或移动 | 返回具体路径失败，由旅行或来源业务决定替代 |
| 旅行或来源时限 | 结束当前尝试，结算清理与已取得物资，再由上层判断换源 |
| 配方规划 | 记录缺口和限制原因，执行当前能够安排的部分 |
| 烟花补给次数或可用来源 | 在符合安全条件时进入资源等待，保留原执行 |
| 未结借盒、工具或库存责任 | 保留恢复义务，按对应业务契约阻止后续不安全操作 |

预算耗尽表达当前投入上限内未完成。换源、报告缺料、资源等待和施工停止由各业务自己的结果契约决定，详见[交付与结果](../supply/delivery)。

## 参数与配置

上述数值多数由对应类的默认策略和常量提供。内部调用可以传入 `SearchPolicy` 或共享预算对象；当前公开命令与服务器配置支持的字段以[执行入口](../reference/executables)和[配置选项](../reference/config)为准。

当前接口没有统一的“任务总预算”参数。调整局部搜索策略、修改某一 Flow 的时限，以及配置测试程序的实际时间上限，分别影响不同的层级。

## 施工补给的进展计时

`ExcavationResourceTrip` 将取货和返回旅行的进展传递给 `ExcavateAreaFlow`。子流程报告阶段推进或移动进展时，挖掘流程更新无进展计时；持续等待继续消耗该计时。各执行范围同时保留自身的总时限，子流程失败由所属流程负责清理并向上报告。

## 如何检查一次超时

1. 找到执行 ID、失败码和报错的组件。
2. 核对该组件的限额、单位及开始时间。
3. 查规划／移动计数、搜索会话统计、维护计数及活动子操作。
4. 查看父执行剩余时间，以及是否发生过明确挂起。
5. 对照实际 TPS、世界进展和测试程序的实际时间上限。

当前预算由多个层级管理。尤其需要区分会话节点额度与累计导航时间、业务等待与明确挂起、补给消耗与父级补偿，以及新子操作与原父范围。调整某个子流程上限时，应同时检查这些边界。
