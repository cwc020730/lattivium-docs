# 需求与规划

物品需求表表达调用者希望取得的物品及数量。规划器将它与已携带物资、Atlas 库存、配方和旅行成本结合，生成来源分配及必要合成安排。

## 需求表

需求表是“物品 ID → 正整数数量”。例如 `minecraft:oak_planks → 6` 表示最终需要 6 个橡木木板。

| 术语 | 具体含义 |
| --- | --- |
| 最终需求 | 调用者要使用或交付的成品数量 |
| 已携带分配 | Bot 原有库存中允许计入本次需求的数量 |
| 原料需求 | 为制造成品而需要消耗的物品数量 |
| 来源库存 | Atlas 对某个容器可提供物资的观察 |
| 已分配数量 | 当前计划安排从来源取得的数量，加上已携带分配 |
| 未分配数量 | 当前收集需求尚未安排来源的部分 |

需求可以从 `.litematic` 统计、从 `.materials.json` 读取，也可以由施工等调用者在内存中生成。文件格式见[输入文件](../reference/files)。物品组件和来源保护策略还会影响哪些实物能够计入需求。

## 三种规划数据

| 类型 | 保存内容 | 使用者 |
| --- | --- | --- |
| `SupplyPlan` | 来源任务、步骤分组、收集需求、已携带分配、交付容器与旅行提示 | 收集流程 |
| `MaterialProductionPlanner.Plan` | 最终需求、所需库存原料、配方批次、预计成品和缺口 | 合成规划与执行 |
| `SupplyRequest` | 收集计划、执行模式、物品筛选策略、打包安排及交付目标 | 已准备好的供给执行 |

带合成时，收集计划的需求常是生产计划的库存原料需求。最终成品目标保存在生产计划中。例如需要 6 个木板，来源可提供 2 个原木：收集安排取 2 个原木，合成安排生产 8 个木板，最终用途预留 6 个，多出的 2 个按实际库存记账。

规划数据描述意图。执行回执记录发生的物品转移；实物数量由取货和合成后的观察核对。

## 来源、聚类与步骤

`ContainerKey` 由维度和容器方块坐标组成，唯一指向一个来源。`SourceJob` 指定该容器要取的物品、数量、步骤编号和旅行提示。

`Step` 是共享步骤编号的一组来源任务。来源在同维度并满足聚类半径时可以归入同一步，所以一步可以访问多个容器。

`SupplyPlanner` 逐次选择能够满足剩余需求、且有可估算路线的来源。当前评分为：

```text
覆盖度 = 对每种剩余物品求和：min(来源库存, 剩余需求) / 剩余需求
旅行成本 = 去程 tick + 已声明返回位置的返程 tick
来源评分 = 覆盖度^(覆盖权重 / 权重总和) / (1 + 旅行成本)^(距离权重 / 权重总和)
```

两种权重默认各为 0.5，分别由 `supplySourceTravelWeight` 与 `supplySourceCoverageWeight` 配置。散装和盒内库存都计入覆盖度。最终分配以通过物品组件与保护校验的实物记录为准。

库存详情有独立的有限读取预算。核验每个容器后，先更新尚缺的成品数量，再优先检查探索次数较少的缺料或配方原料，在同一轮内按上述权重比较来源。这样大量常见材料的容器不会挤掉另一种材料的详情读取。已够用的成品来源放到候选尾部；原料仍可继续检查多个容器，不能因发现少量原料就假定够用。索引数量只用来排序，实际可用数量必须通过详情核验；只有已核验库存能组成满足数量与行程约束的计划时，才结束读取。

| 权重设置 | 选择倾向 |
| --- | --- |
| 距离 0.5、覆盖 0.5 | 同时比较行程成本和需求覆盖度 |
| 提高距离权重 | 更倾向近处来源，容许分多次取货 |
| 提高覆盖权重 | 更倾向集中库存，减少来源访问次数 |

权重按总和归一化，只需调整两者的比例。散装与盒装使用同一评分：整盒库存能满足较多需求时，覆盖度会提高；距离很近的少量散装也可能更划算。未知保护状态的容器需经过现场观察与保护校验，才能成为可取货来源。

选中来源后分配它能满足的数量，以该来源作为下一次出发点继续选择。聚类用于组织访问步骤；路线和来源的实际可达性在执行时校验。

## AtlasSupplyLoadFlow

**输入：**需求文件或内存需求表、交付目标、可用携带库存和执行模式。

**过程：**读取需求 → 查询允许使用的库存与配方 → 分配来源和生产原料 → 调用 `PrepareSupplyFlow` 准备运输容量。

**输出：**`SupplyRequest`；启用生产时还提供生产计划和共享来源查询器。

运输准备可能获取空盒等物资，因此加载流程包含实际执行阶段。纯预览使用 `AtlasProductionPreviewTask`，命令见 [Task 参考](../reference/tasks#atlasproductionpreviewtask)。

## AcquireMaterialsFlow

**输入：**内存需求表、执行模式、可选 `returnTo`。

它调用 `AtlasSupplyLoadFlow`，再调用 `AcquireProductionFlow` 收集和合成。需求全部满足、库存责任结清后，材料留在 Bot 身上；设置返回位置时，还需旅行到该位置才能成功。

`returnTo` 是“维度 + Bot 脚位”，供获取完成后返回。它与交付箱坐标分别表达移动和物品交付目标。获取规划将返程纳入来源成本和路线准入。交付目标列表保持为空，取得的材料留在 Bot 身上供调用者使用。

这个 Flow 是内部复用组件。施工需求的生成与接入边界见[施工物资与补给](../construction/supplies)。

## 重新规划

现场库存不足、来源在预算内不可达或受保护时，收集流程记录已取得物资和失败来源，查询替代来源。配方展开与重新规划使用有限预算。最终取得、缺料和交付如何区分，见[交付与结果](./delivery)。

食物和烟花补给按最低就绪水位的缺口比较来源，取货数量则尽量达到补足目标。下限满足后，可结束额外余量的补取，避免为了上限再访问其他来源。
